# 기능 1: 기도부탁 구현 계획

## 1. 목표와 범위

`project.md`와 추가 요구사항을 기준으로 기도부탁을 작성·조회·수정·삭제하는 기능을 만든다. 관리자가 필드를 추가하면 해당 필드가 작성 폼과 기도부탁 데이터에 반영되는 동적 구조를 사용한다.

### 원문 및 추가 요청에서 확정된 요구사항

- `praycontent`, `praycontentfield`, `password` 테이블을 사용한다.
- 기도부탁의 실제 입력값은 `praycontent.content` JSON에 저장한다.
- 관리자가 정의한 필드를 `content`의 키와 연결한다.
- 지원하는 데이터 타입은 `selectbox`, `selectmultibox`, `checkbox`, `string`, `number`, `date`, `image`, `file`, `bool`이다.
- 필드 표시 방식으로 `badge`, `bold`, `color`를 지원한다.
- `string[]` 데이터는 DB 배열 대신 쉼표(`,`)로 연결한 문자열로 저장한다.
- 관리자 비밀번호 입력 모달을 제공하고 쿠키를 통해 관리자 인증 상태를 판단한다.
- `admin`은 서비스 내 모든 작업을 수행할 수 있다.
- `sub-admin` 권한을 추가하며, 기도부탁(`praycontent`)을 수정·삭제할 수 있다.
- 필드 정보와 그룹화·필터링 설정은 `admin`만 변경할 수 있다.
- `member`는 구성원용 참여 비밀번호로 인증하고 기도부탁을 작성할 수 있다. 비인증 방문자도 목록·상세·게시된 첨부파일을 조회하고 그룹화·필터링을 사용할 수 있다.
- DB는 Supabase PostgreSQL을 사용한다.
- 이미지와 파일은 AWS S3에 저장한다.
- 기도부탁 목록에서 특정 필드 값에 따른 그룹화와 필터링을 제공한다.
- `praycontentfield`에 그룹화 여부와 필터링 여부 컬럼을 추가하며, 관리자가 필드 편집 화면에서 설정한다.

이하에서 원래 요구사항에 없는 세부 동작은 **설계 제안**으로 구분한다. 2026-10-08 요청 반영: 첫 화면에서는 인증 없이 조회하고, 상단 참여 모달에서 인증한 교회 구성원만 작성한다. 서버 연결값은 모두 환경변수로 관리한다. Supabase·S3 모듈은 서버 전용으로 분리하고 반복되는 UI 스타일에는 CSS Modules를 사용한다.

## 2. 현재 프로젝트와 구성 방향

Next.js App Router, React, TypeScript를 사용한다. 공통 UI는 `components/ui`, 기도 기능 화면은 `components/prayer`, 서버 전용 모듈은 `lib/server`에 둔다. 전역 CSS는 색상 변수·기본 스타일로 제한하고 컴포넌트 스타일은 CSS Modules로 분리한다.

구현 시 다음 책임을 분리한다.

| 영역 | 역할 |
| --- | --- |
| 화면 | 기도부탁 목록·작성·상세·수정, 삭제 확인, 권한 인증 모달, 필드 관리, 그룹화·필터링 |
| 동적 필드 처리 | 데이터 타입별 입력 UI, 값 검증, 표시 방식 및 그룹화·필터링 설정 적용 |
| 서버 처리 | Supabase DB 접근, 역할별 인증·인가, 쿠키 검증, S3 업로드·조회·삭제 |
| 공통 데이터 변환 | 쉼표 문자열 직렬화·역직렬화, 날짜·숫자·불리언 처리 |

**설계 제안:** 브라우저는 Next.js 서버를 통해 DB를 조회·변경한다. Supabase API 연결은 URL·publishable key만 사용한다. 기존 비밀번호 모달과 쿠키 인증을 유지하며, Supabase Auth 도입은 초기 범위에 포함하지 않는다. `member`·`sub-admin`·`admin`은 애플리케이션 역할이고 Supabase의 DB 역할과 구분한다.

## 3. 데이터 모델

원문의 테이블명과 컬럼명을 유지하고 추가 요구사항에 필요한 컬럼을 확장한다. Supabase PostgreSQL에서 UUID는 `uuid`, 문자열은 `text`, 날짜·시간은 `timestamptz`, 불리언은 `boolean`을 사용한다. 생성·수정 시각은 서버가 기록하고 UTC로 저장한다.

### 3.1. `praycontent`: 기도부탁

| 컬럼 | 논리 타입 | 용도 및 설계 제안 |
| --- | --- | --- |
| `id` | UUID | 기본 키, 서버에서 생성 |
| `content` | JSON (`jsonb`) | 필드 식별자를 키로 사용하는 입력값 객체, 기본값 `{}` |
| `listdisplaydata` | 문자열 | 목록에서 표시할 필드 식별자를 쉼표로 연결한 값, 기본값 빈 문자열 |
| `createDateTime` | 날짜·시간 | 생성 시각 |
| `updateDateTime` | 날짜·시간 | 마지막 수정 시각 |

**설계 제안:** `content`의 키는 필드 이름 대신 `praycontentfield.id`를 사용한다. 이름을 수정해도 기존 기도부탁의 값을 계속 찾을 수 있다.

JSON 형식 요구사항은 유지하며, 실제 저장 타입으로는 필드 값 조회·그룹화·필터링을 고려해 `jsonb`를 사용한다. [Supabase JSON 문서](https://supabase.com/docs/guides/database/json)

`listdisplaydata`는 기도부탁별로 저장하며, 포함된 필드의 순서를 목록 표시 순서로 사용한다. 작성 화면에서 표시할 필드를 선택하고, 서버는 실제로 존재하는 필드인지 검증한다. 목록에 표시하지 않은 값도 상세 화면에서는 조회할 수 있다.

### 3.2. `praycontentfield`: 사용자 정의 필드

| 컬럼 | 논리 타입 | 용도 및 설계 제안 |
| --- | --- | --- |
| `id` | UUID | 기본 키이자 `content`의 키 |
| `name` | 문자열 | 작성 폼과 상세 화면에 표시할 이름 |
| `datatype` | 문자열 | 원문에 정의된 9가지 타입 중 하나 |
| `displaytype` | 문자열 | `badge,bold`처럼 표시 방식을 쉼표로 연결한 값 |
| `option` | 문자열 | 선택형 입력의 선택지를 쉼표로 연결한 값 |
| `isGroupable` | 불리언 | 그룹화 기준으로 사용할 수 있는지 여부, `NOT NULL DEFAULT false` |
| `isFilterable` | 불리언 | 필터 조건으로 사용할 수 있는지 여부, `NOT NULL DEFAULT false` |
| `createDateTime` | 날짜·시간 | 생성 시각 |
| `updateDateTime` | 날짜·시간 | 마지막 수정 시각 |

두 추가 컬럼의 이름은 설계 제안이다. 서로 독립적으로 설정할 수 있으며 기존 필드에도 기본값 `false`를 적용한다. `listdisplaydata`는 개별 기도부탁의 표시 항목이고, `isGroupable`·`isFilterable`은 전체 목록에서 사용할 수 있는 조회 기준이다.

**설계 제안:** 선택지가 필요한 타입은 `selectbox`, `selectmultibox`, `checkbox`로 한정한다. 다른 타입의 `option`은 빈 문자열로 저장한다. 필드 이름은 앞뒤 공백을 제거하고 같은 이름의 중복 생성을 막는다.

현재 스키마에는 필수 여부, 필드 정렬 순서, 색상 코드, 비활성화 여부가 없다. 초기 버전에서는 모든 필드를 선택 입력으로 두되 기도부탁에는 최소 하나의 유효한 값이 있어야 한다. 필드 순서는 생성 시각과 ID 기준으로 고정하고, `color`는 공통 테마 강조색을 사용한다. 개별 설정이 필요하면 별도 스키마 확장을 검토한다.

### 3.3. `password`: 역할별 인증 정보

| 컬럼 | 논리 타입 | 용도 및 설계 제안 |
| --- | --- | --- |
| `id` | 문자열 | 기본 키, `member`, `sub-admin`, `admin` 중 하나 |
| `pw` | 문자열 | 해당 역할의 비밀번호 해시값 |
| `sessionVersion` | 정수 | 세션 무효화용 버전, 기본값 `1`인 추가 컬럼 제안 |
| `recentDateTime` | 날짜·시간 또는 null | 마지막 로그인 성공 시각, 최초 로그인 전에는 null |
| `createDateTime` | 날짜·시간 | 생성 시각 |
| `updateDateTime` | 날짜·시간 | 인증 정보의 마지막 변경 시각 |

**설계 제안:** 기존 단일 `admin` 행을 구성원·부관리자·관리자 역할별 세 행으로 확장한다. 개인 계정 대신 각 역할의 공유 비밀번호를 사용하는 구조이며, 비밀번호 모달에서 역할과 해당 비밀번호를 입력한다. 역할 선택만으로 권한이 부여되지는 않는다. 개인별 계정이 필요하면 별도 사용자 모델을 설계한다.

컬럼명 `pw`는 유지하되 비밀번호 원문은 저장하지 않는다. 최초 비밀번호는 서버 초기 설정 절차에서 해시로 등록하고 코드나 클라이언트 응답에 포함하지 않는다. 로그인 성공 시 해당 역할의 `recentDateTime`과 `updateDateTime`을 갱신한다. `admin`은 세 역할의 비밀번호를 변경할 수 있으며 변경 시 해당 행의 `sessionVersion`을 증가시켜 기존 세션을 무효화한다.

`password`는 Data API에 노출하지 않는 private 스키마에 두고 서버 전용 DB 연결로 접근한다. 클라이언트에는 역할·인증 상태만 반환하고 해시와 세션 검증용 내부 값은 반환하지 않는다.

### 3.4. AWS S3 이미지·파일 저장

**구현 반영:** 외부 서비스 사용 코드를 숨기라는 추가 요청에 따라 업로드·다운로드 모두 앱의 서버 API를 경유한다. 브라우저에는 S3 URL·버킷·객체 키를 전달하지 않는다. `content`에는 파일 UUID를 저장하고, 비공개 파일 메타데이터가 UUID와 S3 객체 키를 연결한다.

- S3 버킷을 비공개로 운영하고 AWS SDK는 `lib/server/storage/s3.ts`에서만 사용한다.
- 파일은 최대 4MB이며, 이미지 형식은 JPG·PNG·WebP·GIF, 일반 파일은 이 이미지 형식과 PDF·DOCX·XLSX·PPTX를 허용한다.
- 서버에서 인증·파일 크기·실제 파일 형식을 검사한 후 고유한 객체 키로 업로드한다. 기존 객체 덮어쓰기를 허용하지 않는다.
- 미확정 파일은 업로드한 세션에서만 미리보기·저장할 수 있다. 기도부탁에 연결된 후에는 비인증 방문자도 조회할 수 있다.
- `admin`과 `sub-admin`은 기도부탁 수정·삭제에 수반되는 파일 교체·제거를 수행한다.
- 파일의 교체·기도부탁 삭제와 동시에 DB에 정리 대상을 기록한다. 예약 작업이 S3 삭제를 재시도한다.
- 미확정 업로드는 1시간 후 정리 대상이 되며, `POST /api/maintenance`를 주기적으로 실행한다.
- 실제 Supabase·S3 연결은 환경변수 설정 후 별도로 검증한다.

### 3.5. 비공개 운영 테이블

`prayer_private` 스키마의 `password` 외에 다음 테이블을 사용한다. 브라우저 Data API에는 노출하지 않는다.

| 테이블 | 용도 |
| --- | --- |
| `sessions` | 임의 토큰 해시와 만료·버전을 대조하고 로그아웃 시 세션 폐기 |
| `assets` | 파일 UUID·S3 객체 키·소유 세션·연결된 기도부탁·파일 상태 관리, 삭제 재시도 큐 겸용 |
| `rate_limits` | 로그인·작성·업로드의 요청 횟수 제한 |

## 4. 값 저장 및 변환 규칙

### 4.1. 쉼표 구분 문자열

- 화면과 애플리케이션 내부에서는 배열로 다루고, 저장 경계에서 문자열로 변환한다.
- `listdisplaydata`, `displaytype`, `option`과 다중 선택 입력값에 동일한 규칙을 적용한다.
- 빈 배열은 빈 문자열로 저장하고, 빈 문자열은 빈 배열로 복원한다.
- 각 항목의 앞뒤 공백과 빈 항목을 제거하고 중복을 제거하되 최초 입력 순서는 유지한다.
- **설계 제안:** 선택지 자체에 쉼표가 들어가는 경우 저장을 거부하고 안내한다. 단순 구분 방식에서 원래 항목을 복원할 수 있도록 하기 위한 제약이다.
- 일반 `string` 필드의 본문에는 쉼표를 허용하며 배열 변환을 적용하지 않는다.

### 4.2. 타입별 입력 및 JSON 저장 형태

| `datatype` | 입력 UI 제안 | `content` 안의 값 | 검증 |
| --- | --- | --- | --- |
| `selectbox` | 단일 선택 | 문자열 | 등록된 선택지 중 하나 |
| `selectmultibox` | 다중 선택 | 쉼표 구분 문자열 | 모든 항목이 등록된 선택지에 포함 |
| `checkbox` | 체크박스 그룹 | 쉼표 구분 문자열 | 모든 항목이 등록된 선택지에 포함 |
| `string` | 텍스트 입력·여러 줄 입력 | 문자열 | 길이 제한 적용 |
| `number` | 숫자 입력 | JSON 숫자 | 유한한 숫자만 허용, `0`은 유효한 값 |
| `date` | 날짜 선택 | `YYYY-MM-DD` 문자열 | 실제 존재하는 날짜 |
| `image` | 이미지 업로드 | 파일 UUID 문자열 | 허용 이미지 형식·크기 및 업로드 요청 소속 검증 |
| `file` | 파일 업로드 | 파일 UUID 문자열 | 허용 파일 형식·크기 및 업로드 요청 소속 검증 |
| `bool` | 단일 체크박스 또는 스위치 | JSON 불리언 | `true` 또는 `false`, `false`도 유효한 값 |

**설계 제안:** `checkbox`는 복수 선택 그룹으로 정의하여 단일 참·거짓 값인 `bool`과 구분한다. `image`와 `file`은 필드당 파일 하나를 지원하며 파일 바이너리는 JSON에 넣지 않는다. 미입력 값은 해당 키를 생략하며, 값의 유무를 판단할 때 `0`과 `false`를 누락시키지 않는다.

저장 형태 예시:

```json
{
  "content": {
    "00000000-0000-4000-8000-000000000001": "이번 주 시험을 위해 기도해주세요.",
    "00000000-0000-4000-8000-000000000002": "학업,진로",
    "00000000-0000-4000-8000-000000000003": false
  },
  "listdisplaydata": "00000000-0000-4000-8000-000000000001,00000000-0000-4000-8000-000000000002"
}
```

서버는 저장 시 최신 필드 정의를 기준으로 키, 타입, 선택지, 파일 참조를 검증한다. 알 수 없는 키는 거부하며 작성 도중 필드가 변경된 경우 변경 안내와 새로고침 경로를 제공한다.

## 5. 화면 및 사용자 흐름

### 5.1. 기도부탁 목록

- 그룹화하지 않은 기본 목록은 최신 작성 순으로 조회하고 페이지 단위로 불러온다.
- `isGroupable = true`인 필드로 그룹화 기준 선택 UI를, `isFilterable = true`인 필드로 필터 UI를 구성한다.
- 그룹화와 필터링은 함께 사용할 수 있으며 필드 설정을 바꾸는 권한은 `admin`에게만 있다. 목록 이용자는 활성화된 기준 안에서 조회 조건을 선택한다.
- 각 항목은 `listdisplaydata`에 지정된 필드의 이름과 값을 표시한다.
- 필드의 `displaytype`에 따라 배지, 굵은 글씨, 강조색을 함께 적용할 수 있다.
- 긴 내용은 목록에서 일부만 표시하고 상세 화면에서 전체 내용을 확인한다.
- 표시 필드가 없거나 값이 비어 있는 항목도 작성 시각과 상세 링크로 접근할 수 있게 한다.
- 목록이 없는 상태, 불러오는 상태, 실패와 재시도 상태를 제공한다.

### 5.2. 기도부탁 작성·상세·수정·삭제

1. 서버에서 현재 필드 정의를 조회한다.
2. 타입에 맞는 입력 UI를 생성하고 목록에 표시할 필드를 선택하게 한다.
3. 입력값과 파일을 검증하고 저장한다.
4. 완료 후 상세 화면으로 이동한다.
5. 상세 화면은 필드 이름, 전체 값, 생성·수정 시각을 표시한다.

필드가 하나도 없으면 작성 폼 대신 `admin`에게 필드 등록이 필요하다는 안내를 표시한다. `admin` 인증 전까지 필드 관리 동작은 제공하지 않는다.

`admin`과 `sub-admin`에게는 상세 화면의 수정·삭제 버튼을 제공한다. 수정은 기존 동적 폼을 재사용하며 `content`, `listdisplaydata`, 첨부파일을 갱신한다. 삭제는 확인 후 처리한다. 저장 시 서버에서 역할과 최신 필드 정의를 다시 검증하며, 수정·삭제 결과는 목록·그룹별 건수·필터 결과에 반영한다. 동시 수정으로 덮어쓰지 않도록 `updateDateTime`을 이용한 충돌 확인을 제안한다.

### 5.3. 상단 참여 모달 및 필드 관리

1. 첫 화면은 공개 목록으로 시작한다. 상단 `참여하기`를 누르면 역할과 비밀번호를 입력하는 모달을 연다. 인증 후에는 같은 위치의 `권한 변경`에서 다른 역할로 전환할 수 있다.
2. 서버 인증이 성공하면 `admin`에게 전체 관리 기능을, `sub-admin`에게 기도부탁 수정·삭제 기능을 제공한다.
3. `admin`은 필드 이름, 타입, 선택지, 표시 방식, 그룹화 허용 여부, 필터링 허용 여부를 설정하고 미리보기를 확인한다.
4. 저장 후 관련 목록·작성·상세 화면에서 최신 필드 정의를 사용한다.
5. 로그아웃 또는 세션 만료 시 작성·관리 기능을 해제하고 목록·그룹화·필터링 상태는 유지한다.

### 5.4. 필드 기반 그룹화·필터링

활성화 여부를 필드 데이터에 저장하는 것은 확정 요구사항이며, 다음 조회 동작은 설계 제안이다.

- 여러 필드를 그룹화 가능으로 등록하되 목록에서는 한 번에 하나의 기준 또는 `그룹화 없음`을 선택한다. 기본값은 `그룹화 없음`이다.
- 필터는 여러 필드를 동시에 적용할 수 있다. 서로 다른 필드의 조건은 AND, 같은 선택형 필드에서 고른 여러 값은 OR로 결합한다.
- 그룹화와 필터링은 서버에서 처리한다. 전체 조회 허용 데이터에 필터를 먼저 적용한 뒤 그룹별 건수와 목록을 계산한다.
- 그룹화하지 않은 목록은 필터 적용 후 페이지를 나눈다. 그룹화한 목록은 그룹 키·건수 목록을 페이지로 조회하고, 각 그룹의 항목도 별도로 페이지 조회한다. 이미 불러온 한 페이지 안에서만 그룹화하거나 필터링하지 않는다.
- 그룹 내부는 생성 시각 내림차순과 ID로 안정적으로 정렬한다. 그룹 순서는 선택지 등록 순서, 숫자·날짜 오름차순, 그 외 문자열 순서로 정하며 `미입력` 그룹은 마지막에 표시한다.
- 필터·그룹화 기준 변경 시 페이지 상태를 초기화한다. 활성 조건 표시, 개별 해제, 전체 초기화, 결과 없음 상태를 제공한다.

| 타입 | 그룹화 기준 제안 | 필터 동작 제안 |
| --- | --- | --- |
| `selectbox` | 선택지별 그룹 | 선택지 정확히 일치 |
| `selectmultibox`, `checkbox` | 선택된 각 항목의 그룹에 포함 | 쉼표 문자열을 분리한 항목과 정확히 일치; 부분 문자열 검색 금지 |
| `string` | 앞뒤 공백을 제거한 전체 값 | 입력한 문자열 포함 검색 |
| `number` | 숫자 값별 그룹 | 정확한 값 또는 최솟값·최댓값 범위 |
| `date` | 날짜별 그룹 | 특정 날짜 또는 시작일·종료일 범위 |
| `bool` | 참·거짓 그룹 | 전체·참·거짓 선택 |
| `image`, `file` | 첨부 있음·없음 그룹 | 첨부 여부 |

다중 선택값 `학업,진로`는 `학업` 그룹과 `진로` 그룹 양쪽에 표시한다. 그룹 안에서는 같은 기도부탁을 한 번만 세고, 전체 건수는 기도부탁 ID로 중복 제거한다. 따라서 그룹별 건수 합계와 전체 건수는 다를 수 있다.

키 누락·null·빈 문자열은 `미입력`으로 묶고 각 필터에 미입력 조회를 제공한다. 첨부파일 타입에서는 미입력을 `첨부 없음`으로 표현한다. 숫자 `0`과 불리언 `false`는 미입력으로 취급하지 않는다. 문자열 본문은 원문을 보존하고 조회용 값만 정규화한다. 다중 선택 조회는 기존 쉼표 저장 규칙을 유지한 채 서버에서 항목 단위로 처리한다.

서버는 요청된 필드 ID가 존재하고 해당 `isGroupable`·`isFilterable`이 활성화되어 있는지 확인한다. 비활성 필드, 잘못된 타입·연산자·범위는 거부하며 값을 SQL에 직접 이어붙이지 않는다. 관리자가 설정을 해제하면 해당 조회 조건을 무효화하고 화면은 설정을 새로 읽어 조건을 초기화한다.

그룹화·필터링 가능 여부와 `listdisplaydata`는 조회 권한을 제어하지 않는다. 그룹 제목·건수·필터 선택지도 기도부탁 조회가 허용된 범위 안에서만 제공한다. 그룹화·필터링 활성 필드는 표시 항목에 없더라도 조회 기준으로 사용할 수 있다.

## 6. 역할별 인증과 서버 권한

### 6.1. 권한표

| 작업 | 비인증 방문자 | `member` | `sub-admin` | `admin` |
| --- | --- | --- | --- | --- |
| 기도부탁·게시된 첨부파일 조회 | 허용 | 허용 | 허용 | 허용 |
| 기도부탁 작성 | 불가 | 허용 | 허용 | 허용 |
| 기도부탁 수정·삭제 | 불가 | 불가 | 모든 기도부탁에 허용 | 모든 기도부탁에 허용 |
| 설정된 그룹화·필터링 사용 | 허용 | 허용 | 허용 | 허용 |
| 필드 생성·수정·삭제 | 불가 | 불가 | 불가 | 허용 |
| 그룹화·필터링 허용 설정 변경 | 불가 | 불가 | 불가 | 허용 |
| 역할별 비밀번호 관리 | 불가 | 불가 | 불가 | 허용 |

`admin`은 이 기능의 모든 작업을 수행할 수 있으며 입력 검증과 데이터 무결성 규칙은 동일하게 적용한다. `sub-admin`의 추가 관리 권한은 `praycontent` 수정·삭제와 이에 수반되는 첨부파일 처리에 한정한다. 작성은 인증한 교회 구성원으로 제한하고 조회는 공개한다. 현재는 개인 계정 대신 역할별 공유 비밀번호를 사용한다.

### 6.2. 쿠키 인증

쿠키 방식은 유지하며 다음과 같이 구현한다.

- 선택한 역할의 비밀번호는 DB의 비공개 함수에서 SHA-256 전처리와 bcrypt로 검증한다.
- 2026-10-08 요청 반영: 참여·관리 비밀번호의 최소·최대 길이와 문자 조합 규칙은 적용하지 않는다. 입력값의 공백·한글·특수문자를 그대로 보존한다.
- 인증 성공 시 DB에서 생성한 256비트 임의 세션 토큰을 쿠키로 발급한다. DB에는 토큰 해시만 저장하며 유효기간은 8시간이다.
- 쿠키에는 비밀번호를 넣지 않으며 `HttpOnly`, `SameSite`와 운영 환경의 `Secure` 속성을 적용한다.
- 모든 요청에서 DB 함수가 토큰 해시·만료 시간·최신 `sessionVersion`을 검증한다.
- 필드·조회 설정·비밀번호 변경은 `admin`, 기도부탁 수정·삭제는 `admin` 또는 `sub-admin`인지 검증한다.
- 쿠키의 단순 존재 여부, 클라이언트의 `isAdmin` 값, 요청 본문의 역할만으로 권한을 부여하지 않는다.
- 상태 변경 요청은 요청 출처를 검증하고 로그인 시도에는 횟수 제한을 적용한다.
- 로그아웃 시 쿠키를 만료시키며 인증 오류 응답에는 비밀번호 해시나 내부 정보를 포함하지 않는다.
- 비밀번호 변경으로 세션 버전이 달라진 경우 재인증을 요구한다. 사용자에게 비밀번호 해시를 조회하는 기능은 `admin`에게도 제공하지 않는다.

### 6.3. Supabase 접근 경계

- 앱은 Next.js 서버를 통해 Supabase REST RPC를 호출한다. DB 함수에서도 매번 역할을 검증하므로 직접 API를 호출해도 권한 제한이 유지된다.
- 2026-10-07 요청 반영: DB 연결은 `SUPABASE_URL`·`SUPABASE_PUBLISHABLE_KEY`만 사용한다. DB 비밀번호나 secret/service-role key는 사용하지 않는다. 최초 스키마·함수·비밀번호 등록은 생성된 SQL을 SQL Editor에서 실행한다. `password`와 내부 데이터는 비공개 스키마에 둔다.
- Data API 공개 스키마에 있는 테이블은 RLS를 활성화하고 `anon`·`authenticated`에 직접 접근 권한을 부여하지 않는다. 불필요한 기존 테이블·함수 권한도 회수하며 서버용 DB 역할에는 필요한 접근만 부여한다. [Supabase API 보안 문서](https://supabase.com/docs/guides/api/securing-your-api)
- 공개 진입 함수는 SECURITY INVOKER이며 정해진 작업만 비공개 구현에 전달한다. 비공개 SECURITY DEFINER 구현은 고정된 search_path와 자체 세션 검증을 사용한다. Supabase Auth JWT 대신 기존 공유 비밀번호 모델을 유지하며 테이블 직접 접근은 허용하지 않는다. [Supabase RLS 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)
- 그룹화·필터링 조회는 같은 조회 권한을 검사하는 RPC에서 처리한다. 필드·연산자를 검증하고 입력값에는 PostgreSQL의 리터럴 인용을 적용해 SQL 삽입을 방지한다. 실제 쿼리와 실행 계획에 맞춰 JSONB 검색·표현식 인덱스를 검토하며, 쉼표 문자열 검색에 일반 JSONB 인덱스가 모두 적용된다고 가정하지 않는다.

## 7. 기존 데이터와 필드 변경 정책

다음은 데이터 연결을 유지하기 위한 초기 정책 제안이다.

| 변경 | 처리 방식 |
| --- | --- |
| 필드 추가 | 새 작성 폼에 반영하고 기존 기도부탁에서는 미입력 상태로 처리 |
| 이름·표시 방식 변경 | 동일한 필드 ID를 유지하고 기존 값에도 새 표시 설정 적용 |
| 그룹화·필터링 활성화 | 기존 `content` 값에 즉시 적용, 값 자체는 변경하지 않음 |
| 그룹화·필터링 비활성화 | 해당 UI와 조회 조건을 해제하고 관련 조회 캐시 무효화 |
| 데이터 타입 변경 | 해당 필드가 기존 기도부탁에서 사용 중이면 차단 |
| 선택지 추가 | 기존 값에 영향 없이 허용 |
| 선택지 이름 변경·삭제 | 해당 선택지가 저장된 데이터에서 사용 중이면 차단 |
| 필드 삭제 | `content` 또는 `listdisplaydata`에서 참조 중이면 차단 |

참조 확인과 필드 변경은 하나의 원자적 처리로 수행한다. 기도부탁 저장과 동시에 발생할 수 있는 필드 변경도 PostgreSQL 트랜잭션·잠금 방식으로 일관성을 보장한다. 참조 중인 필드를 숨겨야 한다면 비활성화 컬럼 추가와 기존 데이터 표시 정책을 별도로 설계한다. `isGroupable`·`isFilterable`은 필드 자체의 비활성화 여부와 구분한다.

## 8. 구현 순서

1. **미정 정책 결정**
   - 목록·상세·게시된 첨부파일 조회는 공개하고 작성·관리·업로드 API에는 구성원 인증을 적용한다.
   - 역할별 공유 비밀번호 방식과 그룹화·필터링의 세부 조회 동작을 확정한다.
   - 필드 ID를 JSON 키로 사용하는 방식과 `listdisplaydata` 의미를 확정한다.
   - 입력 길이, 필드·선택지 개수, 파일 형식·크기 제한을 정한다.
2. **DB 및 서버 기반 구성**
   - Supabase에 세 핵심 테이블과 필요한 제약조건·인덱스·서버 접근 권한을 구성한다.
   - `isGroupable`·`isFilterable`, 세 역할의 인증 행, 세션 버전과 private 스키마 구성을 반영한다.
   - 역할별 비밀번호 초기 등록 절차와 서버 DB 접근 계층을 만든다.
   - S3 버킷·서버 IAM 권한·업로드 정책과 파일 정리 작업 큐를 구성한다.
3. **공통 필드 처리 구현**
   - 타입 정의, 쉼표 문자열 변환, 서버 입력 검증, 표시 규칙을 구현한다.
4. **역할별 인증 및 필드 관리 구현**
   - 역할 선택 모달, 로그인·로그아웃, 세션·권한 검증, 비밀번호 변경을 구현한다.
   - `admin` 전용 필드 관리에 그룹화·필터링 설정과 기존 데이터 보호를 구현한다.
5. **기도부탁 기능 구현**
   - 동적 작성 폼, 목록 표시 필드 선택, 목록·상세 조회와 두 관리 역할의 수정·삭제를 구현한다.
   - S3 업로드·조회·교체·삭제와 미참조 파일의 정리 절차를 연결한다.
6. **그룹화·필터링 구현**
   - 활성 필드 기반 UI, 타입별 조회 조건, 전체 데이터 집계와 그룹별 페이지 조회를 구현한다.
   - 설정 변경·기도부탁 수정·삭제 시 조회 상태와 캐시 갱신을 연결한다.
7. **동작 검증 및 마무리**
   - 아래 완료 기준을 검증하고 모바일 화면, 접근성, 오류 안내를 확인한다.
   - 실제 Supabase·S3를 연결한 검증 환경에서 전체 작성·조회·관리 흐름을 확인한다.

## 9. 검증 및 완료 기준

2026-10-06 기준 구현과 로컬 검증을 완료했다. 체크한 항목은 로컬 검증 결과이며, 실제 연결·추가 수동 검증이 필요한 항목은 남겨 둔다. 검증 근거와 남은 연결 검증은 [검증 기록](../docs/verification.md)에 구분한다. 실제 Supabase·S3 설정과 검증은 아직 수행하지 않았다.

- [ ] 관리자 필드 추가 후 코드를 수정하지 않아도 작성 폼에 반영된다.
- [ ] 모든 데이터 타입의 입력·저장·조회가 정의된 형식을 유지한다.
- [x] 배열 값의 저장·복원이 가능하고 빈 값·중복·쉼표 포함 선택지가 정책대로 처리된다.
- [ ] 숫자 `0`, 불리언 `false`, 긴 본문, 날짜 값이 손실 없이 표시된다.
- [x] `listdisplaydata`에 지정한 필드와 순서대로 목록이 표시된다.
- [ ] `badge`, `bold`, `color` 및 조합이 목록·상세에서 일관되게 적용된다.
- [ ] 세 역할의 로그인 성공·실패·만료·로그아웃과 비밀번호 변경 후 기존 세션 무효화가 동작한다.
- [ ] `admin`이 기도부탁 CRUD, 필드 관리, 그룹화·필터링 설정, 비밀번호 관리를 수행할 수 있다.
- [x] `sub-admin`이 모든 기도부탁을 수정·삭제할 수 있고 필드·설정·비밀번호 변경은 직접 요청해도 거부된다.
